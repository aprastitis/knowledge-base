# Designing an Agentic-Loop "Skill" for Hermes: What Anthropic and OpenAI Engineers Actually Say (2024–2026)

## TL;DR
- **The consensus from Anthropic and OpenAI engineers is that an "agentic loop" is just a model running *tools in a loop* — gather context → take action → verify work → repeat — and that you should design this loop deliberately, only invoking it for ambiguous, high-value, verifiable tasks, while leaving ordinary conversation as a single model call.** For Hermes, this means a meta-skill that *detects* when a task warrants a loop, *designs* a fit-for-purpose loop (stopping conditions, verification, context strategy, optional sub-agents), and otherwise stays dormant.
- **Anthropic's "Agent Skills" are the ideal delivery vehicle**: a `SKILL.md` file with YAML frontmatter (name + description) that loads via *progressive disclosure* — the description is the trigger, the body loads only when the task matches — which is precisely how you keep the skill from interfering with normal chat. Hermes already implements this exact pattern (skills are progressive-disclosure `SKILL.md` files exposed as slash commands), so the skill is natively portable.
- **The hard-won engineering lessons converge on a handful of controls**: explicit stopping conditions (completion signal, max iterations, budget caps), self-verification with a separate "critic" pass and a hard cap of one-to-three revisions, context management across iterations (compaction, structured note-taking, sub-agents), and named failure modes to defend against (infinite loops, drift, premature stopping, context overflow, hallucinated completion). Hermes's own loop already enforces several of these (default 90-iteration budget, 50% and 85% compaction triggers), so the skill should *cooperate with* those primitives rather than fight them.

## Key Findings

1. **An agent = "models using tools in a loop."** Anthropic's Barry Zhang (AI Engineer Summit, 2025): an agent is "models using tools in a loop," and "three components define what an agent really looks like" — the environment, the tools, and the system prompt. The loop itself is mechanically simple ("often just a while loop"); the intelligence lives in the model, not the harness.

2. **The canonical loop is "gather context → take action → verify work → repeat."** This exact phrasing is Anthropic's, from *Building agents with the Claude Agent SDK*. The "verify" step is what separates real agents from chatbots and is where most quality comes from.

3. **Don't loop for everything.** Both labs are emphatic: use agents only for tasks that are (a) ambiguous enough that you can't pre-map the decision tree, (b) valuable enough to justify token cost, and (c) verifiable. This is the single most important design rule for the Hermes skill's *activation gate*.

4. **Context is a finite resource that degrades ("context rot").** Anthropic's *Effective context engineering* frames the discipline as "finding the smallest set of high-signal tokens that maximize the likelihood of your desired outcome," and prescribes three levers for long-horizon work: **compaction**, **structured note-taking**, and **multi-agent architectures**.

5. **Skills are the right abstraction and Hermes natively supports them.** Anthropic's Agent Skills (open standard at agentskills.io, adopted across Claude, OpenAI Codex, Gemini CLI, Copilot, Cursor) use three-tier progressive disclosure. Hermes Agent implements the same standard and loads skills with `skills_list()` → `skill_view(name)` → `skill_view(name, path)`.

6. **MiniMax (Hermes's recommended engine) is an interleaved-thinking model.** MiniMax-M2/M2.7/M3 wrap reasoning in `<think>...</think>` and *require* that prior-turn reasoning be preserved across tool calls or performance drops sharply. This is a hard constraint the loop design must respect.

## Details

### 1. Conceptual frameworks from Anthropic and OpenAI

**Anthropic — *Building Effective Agents* (Erik Schluntz & Barry Zhang, Dec 2024).** The foundational text. Its key architectural distinction: *"Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks."* It builds everything from the **augmented LLM** (an LLM augmented with retrieval, tools, and memory) and catalogs five composable patterns:
- **Prompt chaining** — decompose a task into a fixed sequence of steps, each feeding the next (trade latency for accuracy).
- **Routing** — classify input and direct it to a specialized follow-up.
- **Parallelization** — sectioning (split into independent subtasks) or voting (run the same task multiple times).
- **Orchestrator-workers** — a central LLM dynamically breaks down tasks and delegates to worker LLMs (used for coding across multiple files where subtasks aren't predetermined).
- **Evaluator-optimizer** — one LLM generates, another evaluates against criteria, and the loop repeats until quality is met.
The guiding philosophy: *"find the simplest solution possible, and only increasing complexity when needed"* — often "not building agentic systems at all."

**Anthropic — the core loop.** From *Building agents with the Claude Agent SDK*: *"Agents often operate in a specific feedback loop: gather context -> take action -> verify work -> repeat."* [Anthropic](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk) The Claude Code architecture is described as a "deceptively simple while loop": a single-threaded master loop that calls the model, executes tools, feeds results back, and continues "until the model decides it's done." [codewithmukesh](https://codewithmukesh.com/blog/anatomy-claude-code-session/) The harness is a "dumb loop" — all intelligence is in the model. [Daily Dose of DS](https://blog.dailydoseofds.com/p/the-anatomy-of-an-agent-harness) Sources of context: the file system, sub-agents, compaction, and **just-in-time retrieval** (the agent uses `grep`/`tail`/`head` to pull only what it needs rather than front-loading everything). [Anthropic](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

**Anthropic — Claude Agent SDK agent loop.** From the docs: the SDK "runs the same execution loop that powers Claude Code: Claude evaluates your prompt, calls tools to take action, receives the results, and repeats until the task is complete." [Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop) Everything accumulates in context (system prompt, tool definitions, history, tool inputs/outputs); when the window approaches its limit "the SDK automatically compacts the conversation." [Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop)

**OpenAI — *A Practical Guide to Building Agents* (PDF, 2025; updated April 2026).** Defines an agent as a system that "independently accomplish[es] tasks on your behalf" and "leverages an LLM to manage workflow execution and make decisions. It recognizes when a workflow is complete and can proactively correct its actions if needed. In case of failure, it can halt execution and transfer control back to the user." Its three core components: **Model**, **Tools**, **Instructions**. It explicitly names the loop: *"This concept of a while loop is central to the functioning of an agent... run multiple steps until an exit condition is met."* Exit conditions include a final-output structured type, or `max_turns`. Recommendation: *"maximize a single agent's capabilities first"* before going multi-agent.

**OpenAI — Agents SDK (the runnable loop).** The `Runner` loops: call the model → if tool calls, execute and continue → if handoff, switch agents and continue → if final output, return. *"If we exceed the max_turns passed, we raise a MaxTurnsExceeded exception."* [OpenAI](https://openai.github.io/openai-agents-python/running_agents/) Key primitives: **Agents**, **Handoffs** (delegation, represented to the LLM as a `transfer_to_<agent>` tool), **Guardrails** (input/output/tool tripwires; input guardrails run only on the first agent, output guardrails only on the final agent), and **Sessions** (state). To prevent infinite loops, "the framework automatically resets tool_choice to 'auto' after a tool call." [OpenAI](https://openai.github.io/openai-agents-python/agents/)

**Context engineering & harnesses (the vocabulary engineers use).** The "harness" is "the complete software infrastructure wrapping an LLM, including the orchestration loop, tools, memory, context management, state persistence, error handling, and guardrails" [Daily Dose of DS](https://blog.dailydoseofds.com/p/the-anatomy-of-an-agent-harness) (LangChain's Vivek Trivedy: *"If you're not the model, you're the harness."*). [Daily Dose of DS](https://blog.dailydoseofds.com/p/the-anatomy-of-an-agent-harness) Anthropic frames context as a "public good" subject to diminishing returns and "context rot" — recall degrades as tokens grow, even below the hard limit. The phenomenon was formally measured in *"Context Rot: How Increasing Input Tokens Impacts LLM Performance,"* Chroma Research (July 2025, by Kelly Hong, Anton Troynikov & Jeff Huber), which tested 18 frontier models (GPT-4.1, Claude 4, Gemini 2.5, Qwen3) and found that "model performance degrades as input length increases, often in surprising and non-uniform ways."

### 2. Concrete implementation patterns

**Stopping conditions / termination.** The harness terminates when: the agent declares completion (returns a plain text response with no tool calls — this is the implicit "done" signal in both Claude Code and Hermes), hits `max_iterations`/`max_turns`, exhausts a cost/token budget, or exceeds an error threshold. [Substack](https://aienhancedengineer.substack.com/p/ai-agents-in-production-the-harness) OpenAI's `max_turns` raises `MaxTurnsExceeded`. Hermes uses a **default of 90 iterations** (`agent.max_turns`, configurable; *not* an immutable hard cap) and at 100% "stops and returns a summary of work done." For self-correction loops specifically, engineers warn that without a termination condition "reflection loops can cycle indefinitely or even degrade quality through over-editing"; [Zylos](https://zylos.ai/research/2026-03-06-ai-agent-reflection-self-evaluation-patterns) standard strategies are **fixed iteration count (2–3 max)**, **quality threshold**, **convergence detection** (stop when revisions produce minimal change), and **external verification** (stop when a test/tool confirms correctness). [Zylos](https://zylos.ai/research/2026-03-06-ai-agent-reflection-self-evaluation-patterns)

**Self-verification & self-correction.** Anthropic's **evaluator-optimizer** pattern (generator + separate critic, looping until criteria met). The Reflexion framework (Shinn et al., 2023) formalized verbal self-critique stored as memory. The critical caveat, repeated across 2025–2026 sources: a single model acting as its own generator and critic "tends to reproduce the same reasoning structure across iterations, with little meaningful correction" [Towards AI](https://pub.towardsai.net/how-multi-agent-self-verification-actually-works-and-why-it-changes-everything-for-production-ai-71923df63d01?gi=9f82af23528d) — so **a separate critic prompt/role is more reliable than inline self-review**, and **execution-based feedback (run the tests, run the code, re-query) is the strongest signal**. Anthropic's own *Harness design for long-running apps* notes agents "tend to respond by confidently praising the work — even when... the quality is obviously mediocre," [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps) motivating a dedicated evaluator agent. Practical rule from production write-ups: cap at one revision cycle, use binary checks not open-ended critique, escalate to a stronger model or human only if validation fails.

**Context management across iterations.** Anthropic's three levers (verbatim from *Effective context engineering*):
- **Compaction** — *"taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary."* [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) In Claude Code this preserves "architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs," [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) then continues "with this compressed context plus the five most recently accessed files." [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) Tune the prompt for recall first, then precision. *"Lossiness is a spectrum, not a binary."* [Vorstel](https://vorstel.com/feeds/blog/effective-context-engineering-ai-agents)
- **Structured note-taking (agentic memory)** — write persistent notes outside the window (`NOTES.md`, `todo.md`, `claude-progress.txt`) and re-inject on demand. Anthropic cites *Claude playing Pokémon* maintaining tallies across thousands of steps. [Inkeep](https://inkeep.com/blog/fighting-context-rot) Manus's pattern: agents "recite objectives into the end of context" via a `todo.md` to fight the lost-in-the-middle problem; and they keep failed actions visible because "erasing failure removes evidence." [Steve Kinney](https://stevekinney.com/writing/agent-loops)
- **Multi-agent / sub-agent isolation** — each sub-agent explores in a clean context window and returns only a condensed summary (1,000–2,000 tokens). [Inkeep](https://inkeep.com/blog/fighting-context-rot)

For long-running work, Anthropic's *Effective harnesses for long-running agents* (Nov 2025) adds the **initializer + coding agent** pattern: an initializer sets up `init.sh`, a `claude-progress.txt` log, an initial git commit, and a `feature-list.json`; subsequent sessions make incremental progress "one feature at a time" [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) and leave structured artifacts (git commits, progress notes) for the next session. *Harness design for long-running apps* extends this to a three-agent planner/generator/evaluator architecture and introduces **context resets** (a clean slate, vs. compaction's in-place summary) to fight "context anxiety." [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**Sub-agents / orchestrator-workers.** Anthropic's *How we built our multi-agent research system* (June 2025): an orchestrator-worker pattern where "a lead agent coordinates the process while delegating to specialized subagents that operate in parallel," [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system) each with its own context window. Results: Claude Opus 4 lead + Claude Sonnet 4 subagents beat single-agent Opus 4 by **90.2%** on their internal research eval, [Medium](https://medium.com/@kushalbanda/how-we-built-our-multi-agent-research-system-5f5e10b2a8d6) at roughly **15× the tokens** of a normal chat. [Substack](https://theaiengineer.substack.com/p/how-anthropic-built-multi-agent-deep) The hard-won lesson is the **delegation contract**: each subagent needs an objective, an output format, guidance on tools/sources, and clear task boundaries — "miss any of the four and the subagent drifts." Effort-scaling rules are embedded in the prompt (e.g., one agent for simple fact-finding, 2–4 for comparisons, 10+ for complex research) because otherwise the lead "over-scales." Multi-agent is best for breadth-first, parallelizable work and worse for tightly-coupled tasks — Anthropic states directly: *"domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today."*

**Tool-use design within loops.** Anthropic's *Writing effective tools for agents*: "a few thoughtful tools targeting specific high-impact workflows," [Steve Kinney](https://stevekinney.com/writing/agent-loops) consolidate multi-step operations into single tools (e.g., `schedule_event` not `list_users`+`list_events`+`create_event`), [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents) return only high-signal results (`search_logs` not `read_logs`), [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents) and use **namespacing** (`asana_search`, `jira_search`) to disambiguate. [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents) The litmus test: *"If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better."* [Steve Kinney](https://stevekinney.com/writing/agent-loops) OpenAI's parallel guidance: some systems handle 15+ well-defined tools while others struggle with fewer than 10 overlapping ones — split agents when tool clarity fails.

**Error handling & recovery.** Keep failed actions visible (evidence for the model). OpenAI's SDK supports retries, max-turn caps, guardrail tripwires, and human-in-the-loop approval (`needs_approval=True` pauses the run as a resumable interruption — "treat approvals as paused runs, not as new turns"). [Openai](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) Anthropic recommends formal rules for repeated failures and tool/credential checks before irreversible actions.

**Loop design by task type.**
- **Coding** — the canonical agent use case (verifiable via tests/CI). Gather (read files, grep) → act (edit, run) → verify (tests, build). Use git for checkpoint/revert; work one feature at a time.
- **Research** — orchestrator-worker with parallel subagents; the lead plans and saves the plan to memory; subagents compress findings; a separate citation pass ensures attribution.
- **File operations / long-horizon** — structured artifacts and progress files; just-in-time file access.
- **Web automation** — plan→act→reflect with fresh evidence each step; graceful recovery from flaky steps (MiniMax-M2's documented strength).

### 3. Anthropic Agent Skills (the delivery format)

**What they are.** From *Equipping agents for the real world with Agent Skills*: "A skill is a directory containing a SKILL.md file that contains organized folders of instructions, scripts, and resources." The `SKILL.md` opens with YAML frontmatter requiring `name` and `description`. Optional subfolders: `scripts/` (executable code), `references/` (docs loaded on demand), `assets/` (templates).

**Progressive disclosure (the mechanism that keeps it dormant).** Three levels:
1. **Discovery** — at startup the agent preloads only each skill's `name` + `description` [Agentskills](https://agentskills.io/home) into the system prompt (~30–50 tokens each). This metadata is the trigger.
2. **Activation** — when a task matches the description, the agent reads the full `SKILL.md` body into context.
3. **Execution** — bundled scripts/references load only when a step needs them.
Anthropic frames this as: "give agents a lightweight index of capabilities, pull in details when needed, and keep context lean." [Swirlai](https://www.newsletter.swirlai.com/p/agent-skills-progressive-disclosure) The model selects skills "through pure reasoning, with description quality directly determining routing accuracy." [Swirlai](https://www.newsletter.swirlai.com/p/agent-skills-progressive-disclosure)

**Authoring best practices.**
- **Start with evaluation** — find capability gaps by running representative tasks, then build skills incrementally (the build-evaluate-iterate pattern).
- **Keep `SKILL.md` concise** — under ~500 lines / ~5,000 tokens; move detail into `references/`. "Use progressive disclosure aggressively. If a piece of information is only needed 20% of the time, put it in a reference file." [Strapi](https://strapi.io/blog/what-are-agent-skills-and-how-to-use-them)
- **The `description` is everything** — it covers both *what* and *when*; include trigger keywords (max 1,024 chars). Name: verb-ing + noun, lowercase-hyphen, max 64 chars, no reserved words ("claude"/"anthropic").
- **Provide code templates, not prose** — agents pattern-match against exact examples.
- **Think from the model's perspective** — watch real trajectories and iterate.

**Relation to conditional/just-in-time loading.** This is the answer to the user's "stays dormant for basic conversation" requirement: because only the description sits in context, the full agentic-loop instructions never enter the window during ordinary chat. They load only when the description's trigger conditions match. (Note: at the Anthropic Code Summit, Nov 2025, Barry Zhang & Mahesh Murag explicitly argued "Stop Building Agents, Build Skills Instead" — skills encapsulate domain expertise as "a concrete step towards continuous learning," [Cto4](https://cto4.ai/p/anthropic-stop-building-agents-start-building-skills/) and "anything that Claude writes down can be used efficiently by a future version of itself.") [Cto4](https://cto4.ai/p/anthropic-stop-building-agents-start-building-skills/)

### 4. Hermes Agent (Nous Research) and MiniMax

**Hermes models vs. Hermes Agent.** Two distinct things. The **Hermes model family** (Hermes 2 Pro, Hermes 3 on Llama 3.1, Hermes 4) are Nous Research's steerable, tool-use-tuned LLMs using **ChatML** and a trained function-calling format: tools defined in `<tools>`, calls emitted as `<tool_call>{...}</tool_call>`, results returned as `<tool_response>`. [Internet10k](https://internet10k.com/en/blog/hermes-3-agent-function-calling-en/) Hermes 3 added "advanced agentic capabilities" [Hugging Face](https://huggingface.co/NousResearch/Hermes-3-Llama-3.1-8B) and RAG citations via `<co>` tags; Hermes 4 supports reasoning in `<think>` tags plus function calls in a single assistant turn. The model "itself decides when a tool is needed and emits JSON with the function name and arguments." [Internet10k](https://internet10k.com/en/blog/hermes-3-agent-function-calling-en/) vLLM/SGLang ship Hermes tool-call parsers (`--tool-call-parser hermes`). [Internet10k](https://internet10k.com/en/blog/hermes-3-agent-function-calling-en/)

**The Hermes *Agent*** (github.com/NousResearch/hermes-agent; MIT; v0.16.0 / tag v2026.6.5, June 6 2026) is a separate, model-agnostic, self-hosted autonomous agent — *"The only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, and builds a deepening model of who you are across sessions."* [github](https://github.com/NousResearch/hermes-agent) [Nousresearch](https://hermes-agent.nousresearch.com/docs/) It is explicitly built around the agent loop rather than a gateway. Nous Research and MiniMax announced a partnership (April 7, 2026) to optimize MiniMax models for Hermes Agent; "MiniMax models are already some of the most-used in Hermes Agent." [X](https://x.com/NousResearch/status/2041705249744789953)

**Hermes Agent loop internals (from Nous's own developer docs).** The core engine is the `AIAgent` class (`run_agent.py`). The **Turn Lifecycle** per iteration: append user message → build/reuse cached system prompt → check preflight compression (>50% context) → build API messages → inject ephemeral layers (budget warnings, context pressure) → apply prompt-cache markers (on Anthropic-compatible endpoints) → make interruptible API call → parse: if tool calls, execute (multiple run concurrently via `ThreadPoolExecutor`) and loop back; **if plain text response, persist and return (the "done" signal).** Three API modes: `chat_completions`, `codex_responses`, `anthropic_messages` (MiniMax is wired through the Anthropic-Messages-compatible adapter). [Nousresearch](https://hermes-agent.nousresearch.com/docs/integrations/providers)

- **Iteration budget:** default **90 iterations** via `IterationBudget` (configurable via `agent.max_turns`); at 100% "the agent stops and returns a summary of work done." Subagents get **independent budgets capped at `delegation.max_iterations` (default 50)**, so total work across parent + children can exceed the parent's cap. (The widely repeated "hard cap of 90 turns" is imprecise — it's a configurable default with a graceful summary-and-stop.)
- **Compaction:** **preflight** summarization triggers above **50%** of context; **gateway auto-compression** (more aggressive) above **85%**. During compression, memory is flushed to disk first, middle turns are summarized, the last N messages preserved intact (`compression.protect_last_n`, default 20), tool-call/result pairs kept together, and a new session-lineage ID generated. User command: `/compress`.
- **Memory:** built-in `MEMORY.md` (~800 tokens / 2,200 chars) and `USER.md` (~500 tokens / 1,375 chars), injected as a frozen snapshot at session start; cross-session FTS5 search over `state.db`; plus 8 optional external memory providers (Honcho, Mem0, etc.). Minimum **64K-token context** required at startup. [GitHub](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/getting-started/quickstart.md)
- **Skills:** progressive-disclosure `SKILL.md` files in `~/.hermes/skills/`, compatible with agentskills.io; loaded `skills_list()` (~3k tokens) → `skill_view(name)` → `skill_view(name, path)`. **Every installed skill is automatically a slash command** [nousresearch](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills) (`/plan ...`). A `<available_skills>` block is injected into the system prompt with a mandatory instruction: "Before replying, scan the skills below. If one clearly matches your task, load it with skill_view(name)." Hermes self-authors skills (via `skill_manage`) after a complex task (5+ tool calls), after finding a working path through errors, after user correction, or on discovering a non-trivial workflow.
- **Sub-agents:** `delegate_task` spawns child `AIAgent` instances with **isolated context** [nousresearch](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation) ("Subagents start with a completely fresh conversation... zero knowledge of the parent's history"); "only its final summary enters the parent's context." [nousresearch](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation) Up to 3 concurrent by default; children inherit the parent's credentials/key pool; leaf subagents cannot call `delegate_task`, `clarify`, `memory`, `send_message`, or `execute_code`. `execute_code` runs Python that calls tools via RPC, "collapsing multi-step pipelines into zero-context-cost turns." [github](https://github.com/NousResearch/hermes-agent)
- **System-prompt ordering (10 layers):** (1) SOUL.md identity → (2) tool guidance → (3) Honcho block → (4) optional system message → (5) frozen MEMORY → (6) frozen USER → (7) **skills index** → (8) context files (`AGENTS.md`, etc.) → (9) timestamp/session ID → (10) platform hint. Design principle: "System prompt doesn't change mid-conversation" (prompt-cache stability) — so per-turn injections (budget/context warnings) are appended to the *user* message, not the system prompt.
- **Plugin hooks:** `pre_tool_call`, `post_tool_call`, `pre_llm_call` (the only one that can inject context, once per turn before the tool loop), `post_llm_call`, `on_session_start`, `on_session_end`.

**MiniMax as the underlying engine.** MiniMax-M2 is a 230B-total / 10B-active MoE "built for Max coding & agentic workflows" [Hugging Face](https://huggingface.co/MiniMaxAI/MiniMax-M2) (MIT, Oct 2025), explicitly tuned for "long-chain tool-calling tasks, coordinating calls to the Shell, Browser, Python code interpreter, and various MCP tools." [MiniMax](https://www.minimax.io/news/minimax-m2) M2.7 has 256 experts, ~204,800-token input context; M3 supports up to **1,000,000 tokens**. [Minimax](https://platform.minimax.io/docs/guides/text-generation) The defining property: **interleaved thinking** — MiniMax reasons in `<think>...</think>` between tool calls in a **plan → act → reflect** loop. The model card is emphatic: *"IMPORTANT: MiniMax-M2 is an interleaved thinking model... you must ensure that the historical content is passed back in its original format. Do not remove the `<think>...</think>` part, otherwise, the model's performance will be negatively affected."* MiniMax's own ablation (post: "Interleaved Thinking Unlocks Reliable MiniMax-M2 Agentic Capability") — retaining vs. discarding prior-round thinking — shows the magnitude: **BrowseComp 44.0 vs. 31.4 (+40.1%)**, **Tau² 87 vs. 64 (+35.9%)**, **GAIA 75.7 vs. 67.9 (+11.5%)**, **xBench 72.0 vs. 66.0 (+9.1%)**, and **SWE-Bench Verified 69.4 vs. 67.2 (+3.3%)**. Within a single user turn, prior tool-call reasoning must be retained; across new user turns, old reasoning can be dropped to save context. [Hugging Face](https://huggingface.co/MiniMaxAI/MiniMax-M2/discussions/38) M2.1's eval scaffold documents an aggressive policy: "When token usage exceeds 30% of the maximum context window, we retain the first AI response, the last five AI responses, and the tool outputs, discarding the remaining content." MiniMax's agent RL framework "Forge" is designed to "optimize the model's generalization across agent scaffolds and tools." [MiniMax](https://www.minimax.io/news/minimax-m25)

### 5. Practical synthesis — how to write the Hermes meta-skill

**Make it a meta-skill, not a fixed loop.** The skill should teach Hermes *how to design a loop for the task at hand*, mirroring Zhang's "models using tools in a loop" reduced to environment + tools + system prompt. Concretely, the `SKILL.md` body should instruct the agent to, on activation, explicitly decide and state: (1) the **goal & success criteria**, (2) the **stopping conditions**, (3) the **verification method**, (4) the **context strategy**, and (5) whether to **delegate**.

**Activation gate (so it stays dormant in conversation).** Put the agentic-loop trigger entirely in the `description` frontmatter, leveraging progressive disclosure. The description should fire only on multi-step, ambiguous, verifiable, or long-horizon tasks ("build", "research", "refactor across files", "automate", "run until done", "process this dataset") and explicitly *not* on Q&A, chitchat, or single-step requests. Reinforce inside the body with Zhang's three-question gate: *Is the decision tree un-mappable? Is the task worth the tokens? Is the output verifiable?* If any answer is no → answer directly without a loop. Because Hermes already injects a "scan skills, load if it clearly matches" instruction and only the description sits in context until matched, this keeps normal chat untouched.

**Recommended loop skeleton the meta-skill should emit:**
1. **Plan** — restate goal, define explicit success criteria and a hard iteration/budget ceiling, write a `todo.md`/progress note (structured note-taking).
2. **Gather context** — just-in-time retrieval; pull only high-signal tokens.
3. **Act** — prefer few, well-scoped tools; one logical step at a time.
4. **Verify** — run an objective check (tests, re-query, schema validation) or a *separate* critic pass; cap revisions at 1–3.
5. **Manage context** — at compaction thresholds, summarize to a progress artifact and continue; for breadth, delegate to a sub-agent with a four-part contract (objective, output format, tools/sources, boundaries) and ingest only its summary.
6. **Stop** — emit a plain-text completion only when success criteria are *checked* as met; otherwise stop at the budget ceiling and report state honestly.

**Failure modes to defend against (name them in the skill):**
- **Infinite loops / runaway iteration** — always set a max-iteration and budget ceiling; cap revision cycles; Hermes's 90-iteration default and OpenAI's `max_turns` are backstops, but the skill should set a *task-appropriate, lower* ceiling.
- **Drift** — recite the goal at the end of context each iteration (`todo.md`); for sub-agents, give explicit boundaries; drift is "hard to detect, late to surface."
- **Premature stopping** — never accept "done" without an objective verification step; coding → tests must pass; research → criteria checklist met.
- **Context overflow / rot** — compaction + note-taking + sub-agent isolation; keep tool outputs lean; remember recall degrades before the hard limit.
- **Hallucinated completion** — models confidently praise mediocre work; require execution-based or separate-critic verification, not inline self-approval.
- **Hallucinated tool selection** — few, clearly-named, non-overlapping tools.

**MiniMax-specific guardrails for the skill.** Because Hermes commonly runs on MiniMax, the skill must instruct: preserve `<think>` reasoning across tool calls within a turn (never strip it mid-loop); rely on interleaved plan→act→reflect rather than one-shot upfront planning; and exploit MiniMax's documented recovery-from-flaky-steps strength in web/coding loops. Respect Hermes's prompt-stability rule — per-iteration state belongs in user-message injections or progress files, not in mutated system prompts.

## Recommendations

**Stage 1 — Build the activation gate first.** Write the `SKILL.md` frontmatter so the `description` is a precise router: enumerate trigger verbs/task-shapes (build, research, refactor-across-files, automate, batch-process, "keep going until") and explicit non-triggers (single questions, definitions, casual chat). Test it the way Anthropic prescribes — run representative prompts (both agentic and conversational) and confirm it activates only on the former. Threshold to proceed: zero false activations on a 20-prompt conversational test set.

**Stage 2 — Author a concise meta-skill body (<500 lines).** Encode the five design decisions (goal/criteria, stopping, verification, context strategy, delegation) and the six-step loop skeleton above. Provide concrete *templates* (a `todo.md` template, a delegation-contract template, a verification-checklist template) rather than prose. Move task-type playbooks (coding, research, web, file-ops) into `references/` files loaded just-in-time.

**Stage 3 — Wire it to Hermes primitives, don't reinvent them.** Have the skill *set* a task-appropriate `max_turns` (lower than the 90 default for bounded tasks), *use* `delegate_task` for breadth-first subtasks with the four-part contract, *use* `execute_code` for mechanical multi-step pipelines (zero-context-cost), and *rely on* Hermes's 50%/85% compaction rather than hand-rolling summarization. Let Hermes auto-author follow-on skills from successful trajectories.

**Stage 4 — Add MiniMax-aware rules.** Instruct preservation of `<think>` across in-turn tool calls; favor interleaved reasoning; and for very long horizons exploit M3's 1M context but still compact, because context rot bites before the hard limit.

**Stage 5 — Evaluate and iterate (build-evaluate-iterate).** Build a representative eval set from real usage; watch full trajectories (not just final scores — "diagnostics on the trace, not the score"); tune the description for routing accuracy and the body for loop discipline. Re-run after every meaningful edit.

**Benchmarks that should change your design:**
- If the skill activates during ordinary conversation → tighten the `description`; it's the router.
- If loops run long or cost spikes → lower the default iteration/budget ceiling and enforce convergence detection.
- If the agent declares done but output is wrong → strengthen the verification step (add execution-based checks or a separate critic).
- If sub-agents duplicate or drift → tighten delegation contracts (objective/format/tools/boundaries) and add effort-scaling rules.
- If long tasks lose the thread → add/strengthen structured note-taking and progress artifacts.

## Caveats
- **Primary vs. secondary sourcing.** Anthropic and OpenAI claims here are anchored to their own engineering blogs, docs, and the OpenAI guide PDF. Some framings (the "harness" vocabulary, failure-mode taxonomies) come from reputable secondary analyses and practitioner write-ups, clearly the community's synthesis rather than first-party doctrine.
- **The "90-turn hard cap" is imprecise.** Hermes's own developer docs describe a *configurable default of 90 iterations* with a graceful summary-and-stop, plus separate 50-iteration subagent budgets — not an immutable cap. Some popular blog posts overstate this.
- **Hermes is fast-moving.** The Agent is at v0.16.0 (June 2026) and some doc pages lag the code: the delegation page still says subagents are synchronous/blocking, but a mid-June 2026 announcement reports asynchronous subagents were added. [MarkTechPost](https://www.marktechpost.com/2026/06/16/hermes-agent-adds-asynchronous-subagents-so-delegated-work-no-longer-blocks-the-parent-chat/) Verify against the running version. The "four-layer memory" and "observe/plan/act/learn" stage labels are community framings, not verbatim Nous terminology (the docs say "closed learning loop" and "background self-improvement review").
- **The 64K minimum context** for Hermes is consistently reported (with a verbatim startup-error string) but was confirmable only via secondary sources within the docs pages reviewed; treat as near-certain but verify on the first-party FAQ if it's load-bearing for your deployment.
- **Multi-agent is expensive.** Anthropic's own number is ~15× the tokens of a normal chat for ~90% better research results — only worth it for high-value, parallelizable, breadth-first tasks, and explicitly *not* for tightly-coupled work like most coding.
- **Forward-looking / vendor-reported statements.** MiniMax/Nous performance benchmarks (e.g., BrowseComp +40.1%, the 90.2% multi-agent uplift) are vendor/lab-reported on their own evals; treat as directional, not independently audited.
